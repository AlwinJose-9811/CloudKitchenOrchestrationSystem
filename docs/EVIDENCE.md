### EV-004  Phase 1: security of MariaDB4j default arguments (finding)
- Supports: NFR-SEC-01; risk note for the embedded database.
- Method: `mariadbd` started by hand as `claude` with exactly the arguments MariaDB4j logged (`--no-defaults --console --skip-grant-tables --max_allowed_packet=64M --basedir ... --datadir ... --tmpdir ... --port ... --socket ...`), on a spare port and a copy of a disposable data directory.
- Results: user `nobody_at_all` with no password logged in over `127.0.0.1` (`SELECT @@skip_grant_tables` = 1, `@@bind_address` = NULL i.e. all interfaces); a user `foo` also connected through the host's non-loopback address `192.0.2.2`; that user could read 31 tables in the `mysql` schema. The installer also leaves anonymous accounts (`''@localhost`, `''@vm`) and a `test` database.
- Conclusion: with MariaDB4j defaults the embedded server is unauthenticated and reachable on every interface of the host. Mitigation is implemented in `DbBootstrap` (EV-005, EV-006).

### EV-014  Phase 1: shutdown hook log visibility, root cause and permanent test (S-14)

#### EV-061 (2026-10-12) D-093 remediation: an administrator can restart a DEAD worker
**Authorization and scope.** The user authorized option (a) of D-093 only: the smallest safe pipeline change that satisfies the existing SRS FR-CON-11 and SDD 7.11.7 / F-43, with no weakening of those documents and no commit, push, tag or release. No other pipeline behaviour was changed.

**Root cause (inspected before editing).** `OrderOrchestrator.restartWorker` is the automatic path (monitor, sweeper); it refuses a dead runtime, as an existing assertion of `WorkerMonitorTest` requires ("no more automatic restarts"), and `StationRuntime.revive()` was never called. The panel called that same method, so a station that had given up could not be restarted. Two further hazards were found while reading the synchronisation: (1) `stop()` drained the workers without the station lock, so a restart arriving from a web thread during shutdown could submit to a closed executor; (2) an operator restart that resets the budget could exhaust the thread pool (`stations + restartMax` threads) if old generations never end, and `RejectedExecutionException` would have reached the servlet.

**Change (source).** `OrderOrchestrator`: new `operatorRestart(code, expectedGeneration, reason)` (compare-and-set on the displayed generation under the station lock; restarts a live or a `DEAD` station; clears the restart history and calls `revive()` after a successful start; refuses a null or unknown station, a stale generation and a stopping application); the shared body of the old restart was extracted unchanged into the private `replaceWorker`, which now also re-checks `stopping` inside the lock and turns a rejected submission into "station stays `DEAD`, return false"; `stop()` takes the station lock around `requestDrain()`. `restartWorker` keeps its automatic semantics. `WorkerControl`: `restartWorker` is replaced by `operatorRestart`. `WorkerPanelServlet`: calls it, says when a `DEAD` worker was revived, and no longer claims the budget as the reason for a refusal. D-095.

**Tests added (nothing removed or weakened).** `OperatorRestartTest` (66): dead station back to IDLE with the waiting order delivered after the next monitor pass; stale, future, unknown and null refused; the automatic path still refuses a dead station; fresh budget (gives up again only after 2 more deaths) and a second operator restart; a healthy worker restarted 4 times with an automatic budget of 1; two operators on the same dead station 20x (exactly one wins); a smoke test of a restart racing `stop` 20x (no exception, no leaked thread); a **deterministic** interleaving of restart and shutdown 20x (the test holds the station lock, parks a restart that has passed its check and a `stop` behind it, asserts that `stop` is `BLOCKED` on the lock, and that the restart is refused and changed nothing); a pool with no free thread (two stuck, interrupt-ignoring generations): refused without an exception, station `DEAD`, and a later restart succeeds. `WorkerPanelDeadWebTest` (6, ordered): a real application whose BIRYANI worker is driven to `DEAD` (restart budget 1): the panel shows `DEAD` with the generation and a Restart button; staff and a forged token get 403; a stale generation changes nothing; the administrator's restart revives it with the flash "had given up and has a fresh restart budget"; the revived station delivers a new order; a second click with the old generation is stale. `WorkerPanelWebTest` (11), `WorkerMonitorTest` and every other existing test are unchanged and pass.

**P8-D2 - orphaned database server after `kill -9` (FIXED in the working tree, awaiting acceptance of D-098).**
- *Superseded design.* The pid-in-a-marker mechanism described below was replaced after the independent review of 2026-10-12 by an operating-system file lock (EV-069, D-098 as now written); the reproduction, the root cause and the drill result below remain valid evidence for the defect and for the first design.
- *Reproduction (isolated drill, real application).* Application started with a throw-away configuration (`/home/claude/ck-drill-load2`, ports 18080/13307); the application JVM (pid 14462, read from the new owner marker) was killed with `kill -9`: the application was gone, the database server pid 14637 kept running and the marker kept the dead pid. #### EV-069 (Phase 8 independent review of D-096..D-100 and DEV-2) Review findings, two fixes, and verification of the final tree
Requested by the user before any commit or tag: an independent read of the five fixes against their requirements and evidence, no commit/push/tag/PR change. Same environment as EV-062. The review read the complete source of the fixes and the shutdown path (`Launcher.RunningApp.close`, `ShutdownCoordinator`, `DbBootstrap`), not the earlier notes.

**What the review found and changed (two defects in my own fixes, both repaired and re-tested).**
1. *D-098 ownership was weaker than claimed.* The first design wrote the application pid into `data/db/.ck-owner` and, at the next start, treated the owner as dead if `ProcessHandle` said so. Problems: (a) pid reuse: a recycled pid of another Java program would block a start, a recycled pid of a non-Java program was guessed away by a name check; (b) a race: two applications started at the same moment could both read a dead owner, and the one that enumerated processes after the other had started its server would stop that server (the window is between a server becoming ready and the marker being written); (c) the marker was written only after the server was up, so a crash during the first-start phase left no marker. *Fix:* ownership is now an operating-system file lock on `<data>/.ck-db-owner` (`FileChannel.tryLock`), taken **before** anything is started and held until the clean stop; the file holds the pid of the owner as information and is emptied by a clean stop. Lock not obtainable = a live application (or another instance in this JVM) owns the directory = `DB_IN_USE`, nothing touched. Lock obtained and the file still names a previous owner = that owner ended abruptly = its server(s) for exactly this `--datadir` are stopped (SIGTERM, forced only after 30 s). Lock obtained and the file empty/new = nothing touched. The operating system releases the lock when the owner dies, so there is no stale state and no pid to compare; two simultaneous starts serialise on the lock. Files: `bootstrap/DatabaseOwnership.java` (rewritten), `bootstrap/DbBootstrap.java` (acquire before anything starts, release after the server is stopped or when a start fails), `test/.../DatabaseHolderMain.java` (new helper main), `DatabaseOwnershipTest` (rewritten, 5 tests).
2. *D-097 reused a certificate without checking its key.* `TlsMaterial.ensure` reused the files if the certificate was unexpired. The two files are written one after the other, so a crash in between, or a file replaced by hand, could leave a key that does not belong to the certificate; the server would then refuse to start (no fallback, because the files exist). *Fix:* reuse requires that a test signature made with the private key verifies with the certificate's public key; otherwise both files are created again. Also: the `tls` directory is set to mode 700; `keytool` is called with `-keysize 256` instead of `-groupname secp256r1` (the latter is not available on every JDK 17 build; only JDK 21 was tested, a JDK 17 build was **not** run); `ensure(dir, validityDays)` exists only so that a test can make a certificate that is about to expire. Tests added to `TlsMaterialTest` (now 6): mismatched key replaced together with the certificate, certificate near expiry renewed, directory 700 and key 600, P-256.
